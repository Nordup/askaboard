# Tutor web parity audit

Baseline: `codex/web-client` at `0f6e1de`. Current SwiftUI source is authoritative. The Paper file `AI Whiteboard Tutor — Design System, Components & Page`, Page 1 (`1-0`), was read directly after loading the Paper guide; this audit uses its read-only artboards 05, 07, 08, 27–34 and their source tree. The implemented behavior also follows `TutorStore`, `MessageThread`, `ActivityTrailView`, `Composer`, `SessionPlanView`, and the current voice source.

## Findings at baseline

| Area | Current Swift behavior and visual source | Web baseline gap |

| Greeting | Current Swift `TutorPanel` and `TutorFullScreen` share the panel treatment: the orb is a separate sibling above `GreetingBlock`, with a 96 × 90 panel face and the panel suggestion layout. Full-screen keeps its 740pt outer lane but caps the live panel-treatment content at 600pt. Paper's 150 × 142 hero remains in the artboard specimen; Swift's current `TutorColumnMetrics.liveScale = .panel` is authoritative for the live screen. | Baseline put the orb inside the greeting and reused panel markup without source start spacing. | Composer | The pill grows to five lines, Shift-Return inserts a line, and a plain Return sends. ## Implementation notes and source boundaries

- The thread now attaches ordered reasoning, tool steps, source batches, board crops, and elapsed time to the assistant message that owns them. Tutor prose stays unboxed, learner turns stay right-aligned, and source/crop disclosures are independently expandable. Crop bytes live in a separate IndexedDB database under a session-qualified key rather than in the workspace document. Orb geometry uses Swift's distinct hero/panel/dock/thread measurements; the live greeting uses panel geometry at both presentations.
- The composer stays mounted across dock/full-screen changes, measures up to five lines, keeps text and upload chips in a session-keyed draft map, and restores the original draft after an accepted edit-resend. The per-session draft map and session-qualified media IDs are deliberate desktop adaptations: Swift keeps plain text in one shared `BoardScreen.composerText` field when switching sessions, while clearing upload attachments because their IDs belong to the old session. The web keeps both text and uploads isolated by session to prevent one session's files from being sent with another session's message.
- A crop send uses `.evaluate` with the learner's exact typed text or an empty learner bubble; a no-capture confused suggestion uses the exact “I don’t know yet.” text and `.dontKnow`. A plan appears only with its paired exercise and outside board work mode. `returnToChat()` is a Swift store capability without a current visible Swift callsite, so this port does not add a new plan-card button for it.
- Web voice continues to use the deployed GPT Live `/v1/live/calls` and `/v1/live/usage` endpoints with the single supported `gpt-live-1` model. Swift's `/v1/realtime/*` endpoints and model choices are a different transport and are outside this web port. For web Live captions, transcript deltas are joined in source-timestamp order without trimming or replacing words; the current [Live conversation transcript delta contract](https://developers.openai.com/api/docs/guides/live-conversations#transcript-deltas) has no final transcript-correction event. Typed turns can run through the existing tutor endpoint during a bound Live call and are mirrored using the documented [typed input delegation pattern](https://developers.openai.com/api/docs/guides/live-delegation#accept-typed-input); unsent files and board crops stay in the draft, as Swift's live composer sends typed words only. This web adaptation posts the submitted text to the ordinary `/v1/turn` tutor endpoint without clipping it, then stores its streamed answer in the workspace transcript. When that session has an awake Live call, only the mirror is capped: `The learner typed: …` goes through `session.thinking.append`, and the backend answer goes through `session.commentary.append`. Each Live append is conservatively bounded to 450 UTF-8 bytes, below the official 500-token per-append limit, without splitting codepoints. This implementation does not claim the commentary was spoken during the smoke; fixtures verify outgoing event JSON and audible behavior requires the real deployed service. Rest closes the provider session and only shows resting after a confirmed close so the duration-based session does not remain billable while idle.
- Fixture tests cover stable activity grouping/refinement, source deduplication, timestamped captions, typed context mirroring, delegation supersession, usage accounting, and crop session isolation. These tests do not verify real microphone capture, provider audio, or spoken quality.

## Voice runtime boundary

The deployed web client currently posts JSON to `/v1/live/calls`, uses the `gpt-live-1` allowlist, and reports duration to `/v1/live/usage`. Current Swift uses `/v1/realtime/calls` with SDP content negotiation, a per-session model choice, and per-response token usage to `/v1/realtime/usage`. This port keeps the web GPT Live transport and labels it accurately. Settings must expose only model choices the selected transport actually accepts. Browser fixture tests establish event handling and presentation behavior; only a real device/browser call against the deployed service can establish spoken-voice behavior.

Voice acceptance is tracked separately from the visual and fixture pass:

- [x] Keep an active call bound to the session that started it; switching chats does not redirect its callbacks, and a typed turn in another chat stays on that chat's tutor pipeline.
- [x] Show connecting/listening/thinking/talking/closing/resting/error states, microphone mute state, and timestamp-ordered input/output captions. A typed turn during an awake call is sent through the current tutor endpoint and mirrored into that same Live call; a resting call follows the normal tutor send path.
- [x] Keep files and board selections attached when typed words are sent during an awake call; Swift routes only typed text into the call. A resting call accepts a normal message with its files or board selection.
- [x] Supersede stale client delegation work and prevent a result from an ended call from entering a later call; fixture tests cover this boundary.
- [x] On provider error or an unconfirmed close, retain error state instead of displaying the call as resting; ending a call accounts for the last confirmed duration.
- [x] Do not invent caption correction semantics: current GPT Live transcript deltas are append-only and timestamped. If the deployed transport adds a correction event, it needs a contract-backed parser and fixture before the UI mutates a caption.
- [x] Confirm the current deployed `/v1/live/calls` and `/v1/live/usage` contract in one authenticated browser call: call creation returned HTTP 200 and final usage returned HTTP 204.
- [ ] Verify microphone capture, provider audio in both directions, wake-after-rest, and spoken quality on a real browser/device. No fixture or static visual counts as spoken-voice verification.

## Real-service smoke — 2026-10-08

- In the authenticated UI, sent one short text request with an empty board. The rendered reply was “Hello! What would you like to work on today?”; a subsequent `GET /v1/sessions/{id}/workspace` returned HTTP 200, revision 2, and both the user and assistant messages. The temporary QA session was deleted after verification.
- Imported and exercised the existing `LiveCall` module in the current browser client. `POST /v1/live/calls` returned HTTP 200; state progressed from connecting to listening, then to talking when a remote audio track played. After a minimum 15-second live interval, `session.close` completed, the client reached idle, and `POST /v1/live/usage` returned HTTP 204. No client errors, transcript callbacks, or delegation callbacks occurred.
- The input was a generated silent WebAudio track. The browser did not access the human microphone. The remote audio track ended, and the client released the peer connection, data channel, microphone stream, and audio element. This verifies transport setup/teardown and endpoint responses only; it does not verify intelligible speech or spoken quality.
- The smoke did not send typed text into the active Live call. Typed web turns remain the documented desktop adaptation: the normal `/v1/turn` request and response are stored, then text is mirrored through `session.thinking.append` and `session.commentary.append` when the same session has an awake call. The original tutor request is untruncated; each optional Live mirror is capped at 450 UTF-8 bytes to remain below the documented 500-token limit. No conclusion about audible commentary follows from the Live lifecycle smoke.
- Final local verification after the Live append-bound regression tests: 15 Vitest files / 74 tests pass, and `tsc -b && vite build` succeeds. Vite still reports the existing large JavaScript chunk warning.
