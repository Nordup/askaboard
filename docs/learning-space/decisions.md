# Learning Space — decision log

Every decision that shaped the app, with the reason and the alternatives
that were rejected. Newest decisions are at the end of each section. When a
decision changes, do not delete it: mark it **Replaced** and add the new
decision below it.

Dates are 2026-10-23 to 2026-10-24 unless stated otherwise.

## The board

| # | Decision | Why | Rejected alternatives |
| --- | --- | --- | --- |
| B1 | **Many boards per folder.** A board is any `*.board.json` file; new boards go to `boards/`. | The founder asked for many boards; the folder structure stays free. | One board per folder. |
| B2 | **Board file: one node per line,** rounded numbers, camera not stored. | Small Git diffs; the camera would change the file on every pan. | Pretty-printed JSON; camera in the file. |

| B4 | **Replaced:** live HTML frames in sandboxed iframes. | First proposal: unlimited, interactive material. | — |
| B5 | **One editable document of nodes** (`ink`, `frame`, `text`, `svg`, `image`). Agent HTML is **converted** into nodes, as in Paper. The learner and the agent have the same rights on every node. | The founder tried live frames and found them rigid and uneditable. Conversion gives full control over rendering and editing. | Live iframes (B4); Paper-style conversion with no ink. |
| B6 | **A node's style is a whitelisted CSS object** that maps 1:1 to inline CSS. The browser does flex layout. | HTML ⇄ nodes conversion becomes trivial in both directions; no custom layout engine. | A custom style model. |
| B7 | **Ink drawn on a frame becomes its child** and moves with it. | Removes the "rigid" feeling: material and the learner's notes are one object. | Loose ink only. |
| B8 | **Replaced by P12 (2026-10-25):** interactive embeds (live, sandboxed HTML) come much later, as a separate node kind. CDN libraries and HTTPS images will be allowed then. | The founder wants interactivity eventually, but editability first. | Interactivity now. |
| B9 | **How P12 is built — program items: the agent's own JavaScript with the full power of the browser's graphics** (2026-10-25). `program(src)` in a scene runs a whole program once, in a worker inside a sandboxed iframe of its own origin (`live-item://`), with the item's OffscreenCanvas: 2D, WebGL 2, WebGPU, its own loop and state. Network is open (fetch, `import` from any URL; bare names from esm.sh); three.js 0.186.1 and its addons plus `ls/interact` (ready-made, optional input code) are served locally. No predefined shapes. The program follows the scene clock (`scene.t`, `scene.step`, tweened `params`) and reports values back (`report`). Input is the program's choice: `input("none" | "enter" | "direct")`; nothing is interactive by default. Storyboard frames run the program at their moment. | The founder: "it should be all JS code, nothing predefined … agents can build incredible 3D worlds with code"; "agents are not dangerous at all"; "3D also should be animatable"; the code decides its interaction. The iframe keeps the item apart from the app page, its storage and files without limiting the code. | A library of 3D primitives; bundling libraries into the worker script; default drag-to-orbit; no network. |
| B10 | **One contract for live items** (2026-10-27, scene stack plan track 1b). Shader, canvas and program items follow item time (`renderer/src/live-pixels/clock.ts`, `host.ts`, `runtime.ts`). While a scene plays an item, item time is the scene's time: a pause holds all three kinds, a seek or a replay moves them, and a move back in time starts a fresh host. Without a scene, item time runs on in real time from where it was. Playback runs at the display's own rate with continuous item time. Previews and stills step through every tick of a 60 Hz grid from the scene's start with a capture barrier, one host per item per preview, on the main window before the snapshot window composes the pictures. Math.random is seeded per item from its mode, code and name (never its id). Items of a scene start their hosts when the scene starts or queues, on screen or not, and keep them until it settles; other hosts start when on screen and end 15 s after they leave it. Hosts take slots (8 units; one per GPU context of a program) and restart after a lost GPU context. WebGL contexts keep their drawing buffer. Program items keep P12's full power. Known limits: a preview's hosts end with the preview (the next preview starts again from tick 0). A program's frame callback both updates and draws, so a still cannot skip drawing. Playback (display rate) and previews (60 Hz grid) are two clocks, so a stateful item can differ slightly between them. Network loads are not waited for: an item that loads data shows what it has at each tick. | Live items had three time models (wall time, none, own loop), so pause, replay and previews disagreed; a preview restarted a program per frame (about 3.2 s of 3.8 s for the EM wave) and could capture a later frame than the one asked; all items started at once, also off screen. GPT review of the scene stack, sections 2 and 5. | Playback on the 60 Hz grid (the founder: no 60 fps cap on 120 Hz screens); a fresh host or a fast-forward when an item comes on screen late (its scene's hosts start with the scene instead); stills in the snapshot window (screenshots wait behind simulations). |
| B11 | **Playback costs what changes on screen** (2026-10-27, scene stack Stage 1, track 1c). The player cuts each scene into units (an object, the edits of one node, an item that html() replaces, the items a replay hides). A unit has a span of time in which its look changes; outside it the unit is evaluated once, inside it once per frame. Overrides that keep their values keep their object, and a frame lists the nodes whose override changed, so the board writes to the DOM only for those. Ink is on two canvases: a static one (the strokes before the animated span of the paint order) and a live one (the animated span, a cached picture of the strokes after it, and the pen tips). No frame loop while every started scene is paused. Timeline values use a cursor per property. Renderer handwriting is seeded from the object and the stroke's points. | The founder's old MacBook Air: playback must never make the pen slow. Before, each frame walked all targets of all scenes and repainted all ink, also the learner's. "Commit the end state, undo it every frame" stays (Stage 2 decides on one frame evaluator). | Tiles of static ink (camera moves repaint anyway; one layer pair is simpler); a second animation engine; lazy frames from the stage. |
| B12 | **One compile per draft; a preview is one capture** (2026-10-27, review fix track C). The main process gives each draft a key; the renderer keeps the compiled draft under it, so preview_scene and play_scene start send only the key and compile nothing (a changed board or stage drops it). A preview with several moments is one snapshot request and one capture: the snapshot window draws the frames as a grid. Framing, close-ups and which live items get stills come from the frames that are drawn. The ink layer redraws only strokes whose look changed in the last 300 ms. | The EM wave draft was sent (13 MB) and compiled again for every preview and start: preview 0.55–0.87 s, start 0.28–0.34 s, and a 145 ms task froze the first frame of every scene. After: preview at "end" 43 ms, every step (6 frames) 90 ms, start 37–43 ms, no freeze; an animated scene over 1,200 learner strokes went from 30 ms to 2.4 ms of work per frame. Review: `drafts/review-sol-final-2026-10-27.md` items 8, 10, 11. | Keeping the descriptions in the renderer (garbage-collection pauses of about 50 ms); one capture per frame (the old storyboard). |
| B13 | **Scene frames cross once, as typed arrays, over a direct port** (2026-10-27). The main process hands one end of a MessageChannel to the stage page and one to the board renderer; the sampled frames of a draft go stage → board as versioned chunks of transferable typed arrays (Float64 numbers, interned path forms, an exact JSON fallback), with job ids, sequence checks, acknowledgements, bounded memory (large objects split across chunks) and cleanup on cancel, reload and crash. write_scene still waits for its frames and the board's compile and returns the board's summary. Sampling order (object-major) and results are unchanged; rebuilds skip sampling as before. | The EM wave draft crossed as 13.1 MB of JSON twice (stage → main → board); now 11.6 MB of typed frames once. write_scene 15–25% faster (EM wave 637–878 ms built); previews and starts unchanged (90–110 ms, about 40 ms). Reviews: `drafts/review-sol-streamed-2026-10-27.md`, `drafts/review-sol-stream-verdict-2026-10-27.md`. | Returning from write_scene before the frames (built, then removed: it only moved the wait into the preview and needed a second lifecycle); sampling on every rebuild (a 5.7 s regression for a write after a draft); on-demand frames (rejected: cannot keep arbitrary JavaScript valid, `drafts/review-sol-ondemand-2026-10-27.md`). |

| T18 | **The stage runs in V8, in a hidden, sandboxed stage process** (2026-10-27, replaces the QuickJS engine of T12; T12 and T14 stay).
