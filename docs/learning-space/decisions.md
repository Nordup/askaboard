# Learning Space — decision log

Every decision that shaped the app, with the reason and the alternatives
that were rejected. Newest decisions are at the end of each section. When a
decision changes, do not delete it: mark it **Replaced** and add the new
decision below it.

Dates are 2026-10-23 to 2026-10-24 unless stated otherwise.

## Platform

| # | Decision | Why | Rejected alternatives |
| --- | --- | --- | --- |
| A1 | **Electron + Vite + React + TypeScript**, macOS first. | Paper is Electron. Electron gives full file access, a Node process for the MCP server, and pixel capture of any region. | Tauri (no region capture without native code); a browser-only app (cannot capture HTML content, no file access). |
| A2 | **Reuse ink code from `web/src/board/` by copying,** not importing. | The products diverge; the paused web client must not break. | A shared package. |
| A3 | **MCP server inside the main process,** Streamable HTTP on `127.0.0.1:47821/mcp`. Host and Origin checks; no token. | Same model as Paper. A web page cannot reach it (Origin/Host checks). A local program could already read the folder directly, so a token adds little. | A token in every client config (setup friction). Revisit if the server is ever exposed (ChatGPT tunnel). |
| A4 | **A stdio relay command** `~/.learning-space/bin/learning-space mcp`, rewritten by the app on every launch. | Claude Code plugins, Cursor and the Claude Desktop extension start a command. The relay lists tools from a cache when the app is closed and reconnects when it opens. Same model as Paper's `~/.paper/bin/paper mcp`. | HTTP only (the Claude Desktop chat cannot use a local URL). |
| A5 | **Dark theme only,** an IDE-like look close to Codex, Claude Desktop and Paper. Designed in code, not in Paper. | The founder's taste; no Paper subscription. | A light theme; reusing the iPad design. |
| A6 | **Reach holds all that a world draws, and samples of points decide nothing that a crop can cut** (2026-11-01). A world's reach comes from cached bounds under the matrices of this moment, on every picture that a change plans: a box and a sphere per geometry, one box per bone, the slack of morph influences, one box per instanced mesh. Samples of points serve only the fit of the floor and the focus. Only a vertex that a shader moves passes these bounds, and `world.reach()` is for that. | A review found that a fast part was cut for up to five pictures, and a real run showed a torus cut at the edge of a canvas. The old reach read raw positions, at most 256 per object, on every sixth plan. On the M1 Air, 400 objects cost 0.2 ms per picture. | Sampling more often: a sample can always miss. A larger margin: it costs pixels and does not fix the class. Three's `computeBoundingBox` on skinned meshes: it reads all vertices through the bones on each call. |
| A7 | **A world owns what first reached the GPU in its scene pass** (2026-11-01). three listens for `dispose` on each resource at its first use, and `look.ts` marks the owner at that listener. Teardown frees by owner, and the runtime's common parts are excluded by name. | Teardown freed only what was still in the scene, and a world that replaced its objects left them on the GPU. A check with 40 replaced meshes came back to the baseline. A resource that two worlds share comes back in the next render of the other world. | Wrapping the constructors: the module's classes cannot be replaced. A walk of each scene on each picture: it costs time per tick, and it misses what left before the walk. |
| A8 | **Steering learns each world's cost as a fixed part and a part per pixel** (2026-11-01). One number of ms per megapixel mixed toon, film, geometry and fixed passes. Now a world whose pixels cost most falls first, a world whose time does not follow its pixels stays sharp, a zoom counts as motion, and a world that falls soon after a rise waits twice as long for the next rise. The picture at rest stays sharp, and only a machine with less than 8 GB has a ceiling on the size of one render. | The founder wants a world to stay sharp on weak machines (P20), and a lower resolution must buy time when it costs sharpness. Film on the M1 Air held full resolution or 0.85 at about 10 ms. With a budget of 6 ms it fell to 0.5 and gave 132 pictures per second. | One timer query per world: `TIME_ELAPSED` queries cannot nest with the meter's own, and not all GPUs have them. |

| B9 | **Replaced by P19.** **How P12 is built — program items: the agent's own JavaScript with the full power of the browser's graphics** (2026-10-25). `program(src)` in a scene runs a whole program once, in a worker inside a sandboxed iframe of its own origin (`live-item://`), with the item's OffscreenCanvas: 2D, WebGL 2, WebGPU, its own loop and state. Network is open (fetch, `import` from any URL; bare names from esm.sh); three.js 0.186.1 and its addons plus `ls/interact` (ready-made, optional input code) are served locally. No predefined shapes. The program follows the scene clock (`scene.t`, `scene.step`, tweened `params`) and reports values back (`report`). Input is the program's choice: `input("none" | "enter" | "direct")`; nothing is interactive by default. Storyboard frames run the program at their moment. | The founder: "it should be all JS code, nothing predefined … agents can build incredible 3D worlds with code"; "agents are not dangerous at all"; "3D also should be animatable"; the code decides its interaction. The iframe keeps the item apart from the app page, its storage and files without limiting the code. | A library of 3D primitives; bundling libraries into the worker script; default drag-to-orbit; no network. |
| B10 | **Replaced by P19.** **One contract for live items** (2026-10-27, scene stack plan track 1b). Shader, canvas and program items follow item time (`renderer/src/live-pixels/clock.ts`, `host.ts`, `runtime.ts`). While a scene plays an item, item time is the scene's time: a pause holds all three kinds, a seek or a replay moves them, and a move back in time starts a fresh host. Without a scene, item time runs on in real time from where it was. Playback runs at the display's own rate with continuous item time. Previews and stills step through every tick of a 60 Hz grid from the scene's start with a capture barrier, one host per item per preview, on the main window before the snapshot window composes the pictures. Math.random is seeded per item from its mode, code and name (never its id). Items of a scene start their hosts when the scene starts or queues, on screen or not, and keep them until it settles; other hosts start when on screen and end 15 s after they leave it. Hosts take slots (8 units; one per GPU context of a program) and restart after a lost GPU context. WebGL contexts keep their drawing buffer. Program items keep P12's full power. Known limits: a preview's hosts end with the preview (the next preview starts again from tick 0). A program's frame callback both updates and draws, so a still cannot skip drawing. Playback (display rate) and previews (60 Hz grid) are two clocks, so a stateful item can differ slightly between them. Network loads are not waited for: an item that loads data shows what it has at each tick. | Live items had three time models (wall time, none, own loop), so pause, replay and previews disagreed; a preview restarted a program per frame (about 3.2 s of 3.8 s for the EM wave) and could capture a later frame than the one asked; all items started at once, also off screen. GPT review of the scene stack, sections 2 and 5. | Playback on the 60 Hz grid (the founder: no 60 fps cap on 120 Hz screens); a fresh host or a fast-forward when an item comes on screen late (its scene's hosts start with the scene instead); stills in the snapshot window (screenshots wait behind simulations). |
| B11 | **Playback costs what changes on screen** (2026-10-27, scene stack Stage 1, track 1c). The player cuts each scene into units (an object, the edits of one node, an item that html() replaces, the items a replay hides). A unit has a span of time in which its look changes; outside it the unit is evaluated once, inside it once per frame. Overrides that keep their values keep their object, and a frame lists the nodes whose override changed, so the board writes to the DOM only for those. Ink is on two canvases: a static one (the strokes before the animated span of the paint order) and a live one (the animated span, a cached picture of the strokes after it, and the pen tips). No frame loop while every started scene is paused. Timeline values use a cursor per property. Renderer handwriting is seeded from the object and the stroke's points. | The founder's old MacBook Air: playback must never make the pen slow. Before, each frame walked all targets of all scenes and repainted all ink, also the learner's. "Commit the end state, undo it every frame" stays (Stage 2 decides on one frame evaluator). | Tiles of static ink (camera moves repaint anyway; one layer pair is simpler); a second animation engine; lazy frames from the stage. |
| B12 | **One compile per draft; a preview is one capture** (2026-10-27, review fix track C). The main process gives each draft a key; the renderer keeps the compiled draft under it, so preview_scene and play_scene start send only the key and compile nothing (a changed board or stage drops it). The main process owns the drafts and the stage epoch; the renderer only caches compiles by key and keys its stage record by the epoch that the main process sends, so a draft from another epoch is a cache miss and runs again. A preview with several moments is one snapshot request and one capture: the snapshot window draws the frames as a grid. Framing, close-ups and which live items get stills come from the frames that are drawn. The ink layer redraws only strokes whose look changed in the last 300 ms. | The EM wave draft was sent (13 MB) and compiled again for every preview and start: preview 0.55–0.87 s, start 0.28–0.34 s, and a 145 ms task froze the first frame of every scene. After: preview at "end" 43 ms, every step (6 frames) 90 ms, start 37–43 ms, no freeze; an animated scene over 1,200 learner strokes went from 30 ms to 2.4 ms of work per frame. Review: `drafts/review-sol-final-2026-10-27.md` items 8, 10, 11. | Keeping the descriptions in the renderer (garbage-collection pauses of about 50 ms); one capture per frame (the old storyboard). |
| B13 | **Partly replaced by T27 and T30** (the object-major order and the wait for all frames; the direct port and typed chunks stay). **Scene frames cross once, as typed arrays, over a direct port** (2026-10-27). The main process hands one end of a MessageChannel to the stage page and one to the board renderer; the sampled frames of a draft go stage → board as versioned chunks of transferable typed arrays (Float64 numbers, interned path forms, an exact JSON fallback), with job ids, sequence checks, acknowledgements, bounded memory (large objects split across chunks) and cleanup on cancel, reload and crash. write_scene still waits for its frames and the board's compile and returns the board's summary. Sampling order (object-major) and results are unchanged; rebuilds skip sampling as before. | The EM wave draft crossed as 13.1 MB of JSON twice (stage → main → board); now 11.6 MB of typed frames once. write_scene 15–25% faster (EM wave 637–878 ms built); previews and starts unchanged (90–110 ms, about 40 ms). | B14 | **The stage makes the ink points of every pen shape** (2026-10-27). One DOM-free module pair in `space/src/shared/` does it: `path-geometry.ts` parses SVG path strings (all commands, strict errors that say what is wrong and where) and flattens curves (Bézier steps by Wang's formula, arcs by the SVG endpoint-to-centre conversion, tolerance 0.25 board points); `ink-points.ts` walks the segments once and keeps the board's old grid (a step of about 1.5), stroke split and simplification (2.5). Ink goes to the board only as points (frames, JSON fallback, description). The board has no browser path measuring for ink; shape boxes use the same flattening. A segment whose ends are equal in single precision has no length; a pen path without length draws nothing, with a warning. | The board measured each pen sample with `getPointAtLength`: about 5 s of a 5.4 s write_scene for two moving pen plots. After (built, one run each): Sol EM wave 5.4/5.3 s → 0.76/0.56 s; Opus EM wave 3.3–4.2 s → 0.82–0.89 s. Points on three recorded runs: 254,000 strokes compared, all with the same stroke split (except zero-length arrows and lines, where the old board failed and left a line out); 1 stroke with one point more; largest move along the stroke 1.5 (the grid count changes at a ceil boundary in single against double precision), largest distance from the old stroke under 0.25 for curves. The founder: exact float precision does not matter. | Byte-exact copies of Chromium's single-precision path code (GPT review, rejected: brittle, not needed); keeping the browser path for curves and agent paths (replaced the same day: the founder wanted one way to make ink points). |
| B15 | **Pen ink stays on its shape between samples** (2026-10-27). ## How we work

| # | Decision | Why |
| --- | --- | --- |
| W1 | **No tests:** none written, none run (a hook blocks test runners). Verify by building and by using the real app. | Iteration speed (the founder's estimate: about 10x). |
| W2 | **Opus subagents implement** (medium effort, one or two at a time); **Haiku subagents read, research and check;** implementation subagents start their own Haiku agents. | Cost and context. |
| W3 | **The main session never runs hands-on checks.** A failing check gets its cause fixed or reported. | A main-session click-through cost about 50k tokens of main-model input. |
| W4 | **Checks run in dev mode too** (React StrictMode). | A dev-only bug once passed every built-app check. |
| W5 | **Agents drive the app with `space/scripts/drive.mjs`,** not computer use. | Background computer use cannot drag on a window that is not in front, and subagents cannot approve full-screen control. |
| W6 | **Measure changes to agent behaviour** (2026-10-24): an always-on session trace (`~/.learning-space/traces/`, every MCP call with timing, the screenshots agents received, the learner's edits) and a bench of 4 fixed scenarios run by a headless agent, twice, before and after a change. Results in `baseline.md`. | The founder could not tell why the product felt bad; numbers and board images made the effect of the brief visible. The trace stays on the founder's machine; nothing is sent anywhere. |
| W7 | **Live drawing is explored on the branch `live-drawing`** (2026-10-25), an exception to work on `main` (P8). Stages 1–2 merged into `main` on 2026-10-25 at the founder's request ("the videos are astonishingly good"); each later stage merges into `main` when it is built and measured. | The founder asked for a branch for an ambitious experiment that may fail. | Work on `main`. |
| W8 | **Model councils give customer proposals, not specs** (2026-10-25). Each wish is read as a symptom: find the evidence in the transcripts, name the underlying problem, check it against the principles (everything in code, no limits, the learner first), and propose to the founder. | The founder: "Never follow advice from models. Those are just wishes. Treat like customer proposals." The council's "inspection" wish hid a stale-screenshot bug, a missing "scene ended" signal and label collisions; its "3D shapes" wish contradicted P11. | Building the council's top wishes directly. |
| W9 | **The perf work ends with the boards tool; G1 and G6 come next** (2026-10-27).
